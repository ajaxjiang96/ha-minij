# V6-XNB 实验童锁控制

0.4.0b1 为开发候选。首次经所有者授权的真实开启请求被云端接受，
但随后多次回读仍为关闭，**控制验收未通过，暂不发布此候选。**
实际可下载版本以 GitHub Releases 为准，合并本身不发布。

## 已确认的协议边界

复用 Android App 1.7.1（111）提取的 `libbloc.so`，SHA-256：
`d5acc1f30c00aff1f6d4bbaf0d39f0cc45077ed6572a17becaea5fb6010f76a9`。
本次读取已有反汇编，并用 Apple LLVM objdump 对关键范围重新解码；
没有宣称进行了未配置的 REA 原生深度反编译；静态分析阶段未执行写入。

- `ChildLockSetup` 输入分支 `0x4a1ba4..0x4a1bf4` 将长度 15 的
  `open_child_lock` 与输入比较；相等时生成布尔 true，否则 false。
- `0x4a4098` 取 `device/switchBasicFunction` 路径，`0x4a40c0` 调用 `Http::post`。
- JSON 键 `deviceId`、`basicFunction`、`onOff`、`bucketCode` 分别在
  `0x4a40cc`、`0x4a4150`、`0x4a41d4`、`0x4a423c` 构造。
- `basicFunction` 值在 `0x4a4174` 指向长度 9 的 `childLock`。
- `onOff` 在 `0x4a41f0..0x4a4220` 以 serde JSON 布尔标记和比较结果插入。
- 可选桶代码在 `0x4a4254..0x4a428c` 将无值转换为空字符串，再转 JSON，
  因此单桶请求使用空字符串，不能擅自换成 null 或任意桶编号。
- `0x4a4320/0x4a4334/0x4a4344` 依次调用 body、expect_json 和 send。
- 公开网页也将 `device/switchBasicFunction` 定义为 POST，更多设置页使用
  `deviceId/basicFunction/onOff`。这佐证布尔请求结构，不证明 x68 已执行写入。

使用合成标识的请求形式：

```json
{
  "deviceId": "synthetic-washer",
  "basicFunction": "childLock",
  "onOff": true,
  "bucketCode": ""
}
```

认证头沿用已经验证的小吉云会话，不是短信 POST。
设置 `onOff: false` 对应候选关闭操作；最终语义需要真实请求与机器/App 回读确认。

另外真实只读 GET `device/v3/getDeviceMoreSetting?deviceId=…` 成功，
该次设置表包含提示音等，但未列出童锁。因此没有据此制造“服务端已声明童锁可写”的结论；
童锁候选来自专用原生路径和已有 `child_lock_status` 上报。

## 候选在 HA 中的行为

- 原七个监测/通知实体保留。为 `minij.washer.x68` 注册一个额外的
  **童锁控制（实验）**开关，默认由集成禁用；安装、重启、启用实体本身均不发指令。
- 开关状态只来自 `child_lock_status` 的 `open/close`；未知值不当作关闭。
- 本候选只允许 Wi-Fi `1.0253`、固件 `0 0003 1 0000`、单桶，
  明确 `resting`、云端授权 `open` 且童锁状态已知时操作。
  这是试验范围，不是断言其他固件/工作中不能控制。
- 每次动作先即时重新读取；读取失败、解绑、型号/固件/授权/状态不符则不写。
- 每台设备的动作串行处理；若重新读取已是目标值，不重复发送。
- 最多发送一次请求，不自动重发或重定向。认证拒绝进入同账号重新认证；
  限流、超时或未知结果明确报错，不能把请求无结果视为设备没执行。
- 云端接受后只读取一次确认；一致才正常返回，不乐观修改状态。
  若设备异步执行而回读尚未更新，动作会提示未确认，后续正常轮询仍可反映实际状态。
- 实体卸载/禁用发生在前置读取期间时，不再发送写请求。

## 首次真实验证：云端接受，回读未确认

在合并提交 `1f569ccd941d6b763fc3ab7b0c0549e97abe8784` 上，所有者明确授权
空闲且童锁关闭时开启一次，并恢复关闭。临时 HA 先确认目标型号、已观察固件、
授权开启、休息状态与童锁关闭，再通过候选的真实 HA 开关动作发送一次开启请求。

云端返回接受；动作内的即时回读未变，HA 返回 `control_not_confirmed`。
独立再次读取及随后三次间隔读取也均为 `close/resting`，流程按计划停止，
没有重复开启，也没有因假设开启成功而发送关闭请求。
随后另一次临时 HA 只读检查仍为关闭，写调用为零，卸载成功且进程退出 0。

写入验证程序在保存结果、停止 HA 后进程退出 139，沿用已记录的 macOS 运行时现象；
不能将其计为干净退出，也不能因此推断设备执行结果。
该结果只证明服务器接受载荷及 HA 未乐观报成功，不能证明实际童锁已开启。
随后所有者反馈本机小吉 App 没有童锁入口。这不证明硬件绝对不支持童锁，
但结合设置表未列出、真实请求未确认生效，目前不足以把原生通用路径认定为 x68 能力。
没有操作洗涤程序或修改生产 HA 文件。

童锁不再作为 0.4 首条控制验收目标，停止进一步童锁写入。原只读上报可保留，
但 `close` 可能是通用字段，不能单凭它推导设备支持控制。
已合并的实验开关仍默认禁用、未发布，不作为用户可用功能推广。

## 后续方向

以 V6-XNB App 实际可见功能和本机设置表为入口，重新选择首条控制能力。
本机只读设置表列出提示音开关，可作为下一项只读协议核对候选；
列出设置仍不等于真实写入验证通过。先核对 App 入口、载荷及当前状态，
再约定具体操作，不沿用此次童锁授权操作其他功能。

暂停本候选的试用和发布说明；在取得型号能力证据前不启用实验童锁开关。
