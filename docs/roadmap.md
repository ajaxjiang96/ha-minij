# 小吉 Home Assistant 完整集成路线图

更新于 2026-10-26。首个云端监测稳定版 `v0.1.1` 已发布。
下一目标是把 V6-XNB 做成可长期使用、可自动化、按已验证能力控制的完整 HA 集成，
再扩大到其他型号。以下版本是规划范围，不是发布日期或功能支持承诺。

## 什么叫“完整”

用户能独立安装、登录、发现自己的设备，读懂运行、阶段、完成和故障，
配置可靠的自动化，并在型号和授权允许时操作设备。认证过期、网络恢复、
HA 重启和集成升级都有清楚的恢复路径；不需要开发者长期协助维护。

“完整”按型号的真实能力判断。App 的通用字段不代表每台机器都支持，
暂时无法确认的能力明确写为未知或不支持。云端集成可以先完整交付；
局域网、固件更新和进入 HA Core 分别评估，不作为人为阻塞全部工作的前提。

已观察空闲→工作→空闲，尚不能区分正常完成和取消。真实重新认证、升级前后全部
原始 ID/自动化引用逐项比对、独立用户安装和长期会话仍待验收，不能因稳定版发布而勾选。
详细历史证据见[首版验收记录](stable-release-checklist.md)。

## 阶段与依赖

| 阶段 | 目标 | 主要依赖 | 发布门槛 |
| --- | --- | --- | --- |
| M1 / 0.2 | 可靠监测与独立使用 | 现有云读取 | 认证恢复、状态展示、独立安装和持续使用记录 |
| M2 / 0.3 | 完成、异常与时间自动化 | 日常周期对照；M1 的恢复/陈旧数据处理 | 正常完成与取消可区分，重载/轮询不误报；时间字段逐项验真 |
| M3 / 0.4 | V6-XNB 已支持能力的控制 | 命令协议和授权；M1 可靠回读 | 每条指令有实际设备回读、失败处理和所有者验收 |
| M4 / 1.0 | V6-XNB 完整使用体验 | M1–M3 中已确认可支持的能力 | 新用户可独立安装、监测、自动化与控制，已知限制明确 |
| 持续扩展 | 更多型号、社区分发 | 独立所有者证据 | 每型号支持矩阵与回归；分发渠道实际通过审查 |

M1 的长周期观察与 M2 的日常取证可并行；控制协议可先研究，真实指令验证另行约定。
不等待不可控的令牌过期才开发其他能力，也不以时间到期自动宣布通过。
某字段或指令若确实不受支持，记录结论并调整范围，不伪造替代值。

## M1：可靠监测与独立使用（进行中）

`0.2.0b1` 已发布，所有者反馈本机验收完成；已实现状态翻译、原始别名保留、空闲上下文、失败退避和成功读取时间。
代码覆盖与真实验收分列于[0.2 验收记录](monitoring-acceptance.md)，
14 天观察及独立所有者反馈仍需各自证据，不因代码提交或笼统验收反馈而勾选。

- [ ] **状态展示**：整理已知别名、中文/英文翻译和原始值；有证据才将状态变成明确枚举。
  空闲时程序/阶段的旧值要能被用户识别，不能当作当前洗涤阶段；未知值继续保留。
- [ ] **恢复路径**：复核网络超时、服务端故障、认证拒绝、账号无设备和设备解绑的区别，
  检查重试/退避及日志脱敏；不能将每次错误解释为令牌过期。
- [ ] **真实会话验收**：自然遇到过期时检查同账号重新认证；比对设备/实体 ID、
  自定义名称、区域及已有自动化引用。只有发现真实刷新机制才实现自动续期。
- [ ] **持续使用**：记录至少 14 天正常使用的版本、可用性、故障恢复和 App 共存结果；
  这仅是首轮观察窗口，不宣称证明令牌有效期或所有云端行为。
- [ ] **独立安装**：至少另一位所有者仅按中文 README 完成安装、登录、重启恢复与诊断反馈。
- [ ] **安装体验**：复核受支持版本的图标、翻译、HACS 稳定/测试更新、备份及排障步骤。
  本机 `entity_picture` 自定义只解决当前安装，不能计为 HACS 上游已修复或其他用户已通过。

**验收**：提交可复核的真实观察摘要与自动化测试结果；未出现的过期场景仍列待验证。
若只拿到部分证据，可继续发布明确标注限制的增量版本，不把 M1 全部标为完成。

## M2：完整周期与自动化（进行中）

0.2.0b1 已发布，所有者反馈 0.2 本机验收完成；持续观察和独立用户证据另列，未虚构时长。
0.3.0b1 已发布，新增经 App/API 对照的剩余分钟数、诊断原字段和异常通知示例；
[周期协议证据](cycle-protocol.md)列出已确认和缺口。
后续所有者确认正常结束回休息并收到完成通知；真实消息接口已返回洗衣完成。
[0.3.0b2](https://github.com/ajaxjiang96/ha-minij/releases/tag/v0.3.0b2) 已发布，进一步实现独立消息读取、完成/清洁完成/故障事件、去重和恢复基线；
暂停/取消字段及候选真实新消息交付仍待验收，M2 整体保持进行中。

- [ ] **状态证据表**：按[日常观察指南](cycle-validation.md)，对照机器、App 与云端，
  记录启动、阶段、明确完成和日常暂停/取消；记录型号、固件及时间来源。
- [ ] **结束原因**：寻找明确完成字段/事件及周期标识，区分成功、取消、停止、失败和未知。
  不能只由 `working → resting` 推断成功；缺少可靠依据时保留原始状态自动化。
- [ ] **完成自动化**：确定 HA 中合适的事件/触发方式，并处理首次加载、重启、重新认证、
  重复轮询、云端恢复和旧状态重放。每个可识别周期最多产生一次完成事件；
  若轮询会漏过短暂事件或云端没有事件历史，明确可能漏报，不能承诺恰好一次送达。
- [ ] **剩余时间**：确认单位、特殊值、暂停、烘干、结束和空闲行为；
  可支持时提供原始剩余时间及适当的预计结束时间，标明云端估算，不能用本地倒计时伪造精度。
- [ ] **异常和在线**：确认 `device_exception`、故障码及上报在线标志的来源、更新时效；
  分开表达云端请求失败与设备上报离线，未知故障保留原文，不捏造诊断。
- [ ] **自动化示例**：提供用户自行启用的完成/故障通知示例，说明重复和恢复行为；
  不在用户实例中自动创建通知或洗涤操作。

**验收**：正常完成、取消/暂停、恢复与重复上报分别有合成回归；承诺的设备语义
有真实周期对照。仅提供取得证据的实体/事件，其余保留明确缺口。

## M3：逐条增加 V6-XNB 控制

研究入口是 App 的实际命令、载荷、授权和回读，不把反编译中的字符串当作可用 API。
先实现一条所有者选定、设备确实支持的指令，再按相同流程扩展。

新增 [MIoT v17 与参考库分析](miot-reference.md)：借鉴能力和权限驱动的实体设计，
不将米家 `v17` 的服务编号、枚举或写权限套到小吉云 `x68`。
所有者确认当前设备只能使用小吉 App，继续沿用小吉云；不另加米家认证依赖。

| 候选能力 | HA 表达候选 | 必须确认 |
| --- | --- | --- |
| 童锁 | `switch` | 是否可远程写、锁定语义、拒绝与真实回读 |
| 程序与参数 | `select` / `number` | 型号允许值、温度/转速等单位和范围、运行期间限制 |
| 启动/暂停/继续/取消 | 合适的按钮或动作 | 云授权、门锁和状态前提、动作是否可重试、实际设备结果 |
| 其他 App 功能 | 按实际语义选择 | V6-XNB 支持情况与完整证据，逐项纳入 |

- [ ] 形成脱敏的命令/状态映射，区分“服务器已接收”和“机器已执行”。
- [ ] 使用 HA 标准实体和动作；校验已知能力、允许值和前提，不能绕过设备保护或云端授权。
- [ ] 写后回读验证、超时/拒绝明确报错；不乐观显示成功，不自动重发可能重复执行的动作。
- [ ] 每条真实指令先与所有者约定设备状态和验证操作；当前路线图不授权启动、停止或修改洗涤。
- [ ] 覆盖不支持的型号/参数、授权关闭、故障、超时、重复提交及回读不一致。

**验收**：每个暴露的控制均完成请求→响应→真实设备变化→HA 回读，
有错误路径和中文说明；无法验证的指令不进入正式控制界面。

## M4：1.0 完整体验与维护

- [ ] 发布 V6-XNB 能力矩阵：已支持、设备不支持、证据不足分别列明；
  监测/完成/时间/故障/控制各有真实验收记录，不能把仍需研究的功能写成支持。
- [ ] 新用户按中文指南完成安装、重启、监测、自动化和其设备支持的控制，
  无需复制开发者日志里的令牌或依赖开发者本机工具。
- [ ] 核对多设备/多账号隔离、添加移除、升级/重载和自定义设置保留；
  合成覆盖与真实多设备证据分开记录。
- [ ] 按 HA 当前质量规范做逐项自评：类型、非阻塞 I/O、配置流程、诊断、
  可用性、异常、翻译和文档；自评不等于官方质量等级认证。
- [ ] 完善支持版本、云 API 变更处置、故障反馈和发布检查；保留未知值反馈路径。
- [ ] 对确切 1.0 候选提交检查 CI、安装包、隐私和实际升级；合并、发布和设备验收分开记录。

**验收**：以上承诺的 V6-XNB 用户旅程可独立完成，所有发布能力有明确证据。
若关键能力不可得，先调整并说明 1.0 范围，不能仅为版本号宣布“全功能”。

## 社区、多型号与分发（持续推进）

- [ ] 将每个新型号作为独立支持项收集脱敏样例、型号/固件和所有者验收。
  先按已证实的能力组织小型映射；确有多型号差异时再抽象，不预建通用家电框架。
- [ ] 使用脱敏固定样例回归缺字段、未知枚举和不同能力；不能仅依据型号名称启用控制。
- [ ] 满足申请时的实际要求后提交 HACS 默认列表/当时推荐的分发渠道，
  跟进图标和独立安装反馈；提出申请与被收录分开记录。
- [ ] 将每阶段拆成可验收的 Issue 和小 PR；记录证据、缺口、依赖及完成条件。
  CI/审查通过后发布，不把文档计划当作已实现功能。

## 独立研究方向

- **局域网/BLE/MQTT/WebSocket**：调查发现、认证和订阅能力；BLE 配网线索不能证明本地控制。
  只有可重复验证且能维护的协议才进入实现，云端中断不能假装本地仍可用。
- **固件**：先记录当前基线；仅由所有者决定升级后比较前后兼容性。
  固件安装不纳入近期 HA 功能，不能把 HACS 集成更新与设备固件升级混淆。
- **HA Core**：先确认当前接纳要求和维护责任，确有提交需要时再拆独立 API 库；
  HACS 分发不依赖 Core 收录，也不预先承诺审核结果。

## 每次推进怎么判定完成

每个工作项记录：目标型号/固件、公开脱敏证据、自动化覆盖、实际验收结果和仍未知的行为。
先完成可验证的一小层并发布，再扩大范围。日常使用补证据，不人为制造故障、
限流、失效会话或额外洗涤来填勾选框；不公开手机号、令牌、设备标识、原始抓包或厂商源码。

下一执行项是 **0.3.0b2 新消息的实际交付验收与 x68 控制能力的只读追踪**：
正常使用时核对官方新完成消息，继续积累周期证据；按 MIoT 参考结构整理本机能力，
优先调查童锁的实际写入路径。未约定真实设备操作前不发送控制指令。
